======================================================================
0. DOCUMENT CONVENTIONS
======================================================================

MUST / MUST NOT: mandatory requirement / prohibition.
SHOULD / SHOULD NOT: recommended unless an approved rationale says otherwise.
MAY: optional.
TBD: unresolved; it is not an approved constant or assumption.
DRAFT: not approved for model release.

This document defines what a regression target means, how a target value is produced, aligned to a sensor observation, validated, versioned, and consumed during training/evaluation/inference. It does not choose a scientifically valid landslide predictor without evidence.

Safety boundary:
- This is a prototype-level monitoring system, not a certified landslide early-warning system.
- A regression output is not a probability of landslide unless a separately validated probabilistic method and calibration evidence explicitly support that claim.
- Model output MUST NOT be the sole safety mechanism or the sole basis for evacuation, emergency response, or other high-consequence decisions.
- A sensor reading, a model score, an observed condition, and an actual landslide event are distinct concepts.

======================================================================
1. PURPOSE AND SCOPE
======================================================================

TCS establishes the canonical contract for:
1. Target meaning and intended use.
2. Target type, unit, range, direction, and encoding.
3. Ground-truth evidence and annotation responsibility.
4. Temporal alignment between input window and target.
5. Label quality, uncertainty, missingness, and exclusion.
6. Dataset splitting and leakage prevention as applied to targets.
7. Training, evaluation, deployment, and runtime interpretation.
8. Versioning, traceability, acceptance gates, and unresolved decisions.

TCS owns target semantics. DSD owns dataset lifecycle, records, splits, manifests, and provenance. DOP owns operational collection, labeling workflow, ground-truth procedure, quality KPIs, and freeze governance. FSS owns feature definitions and model-input compatibility. ICD owns firmware interface and data-quality semantics. LLD owns runtime implementation design.

If these documents conflict:
1. Approved TCS owns target meaning and target encoding.
2. Approved FSS plus actual Edge Impulse deployment metadata owns model-input contract.
3. DSD owns dataset representation, split, and provenance conventions.
4. ICD owns firmware interface/status semantics.
5. A conflict MUST be recorded and resolved through controlled revision; implementers MUST NOT silently infer a resolution.

2. CURRENT PROJECT CONTEXT AND KNOWN LIMITS
======================================================================

Known project context:
- Runtime target: ESP32-S3, offline inference.
- Software stack: Arduino/FreeRTOS and PlatformIO + VS Code.
- ML approach: Edge Impulse Regression is a provisional baseline.
- Candidate sensors discussed: IMU/accelerometer, soil-moisture sensor, YL-83 board, and HX710B ADC with an as-yet-unidentified transducer.
- Actual sensor models, mounting, calibration, sample rate, window length, stride, and exported model metadata are not yet fully approved.

Important limits:
- FSS v1.0 lists candidate channels, not a frozen feature schema.
- YL-83 output MUST NOT be called rainfall without a validated calibration and a defined reference method.
- HX710B raw counts have no physical interpretation until the attached transducer, wiring, measurement quantity, range, and calibration are known.
- IMU tilt estimates depend on axis frame, mounting, gravity-dominant assumptions, sign convention, and calibration.
- A target cannot be selected merely because it correlates with available sensor channels or is convenient to train.
- A target defined from the model's own output is circular and MUST NOT be used as independent ground truth.

No numerical target range, label threshold, forecast horizon, sample rate, window length, or acceptance metric is approved by this document. Those remain TBD until evidence and owner approval are recorded.

======================================================================
4. TARGET SELECTION PRINCIPLES
======================================================================

4.1 Select a measurable target, not a vague concept

The phrase “landslide risk” is too broad to serve as a regression target unless it is operationally defined and backed by an appropriate reference process. A target MUST be observable or reproducibly derived from documented independent evidence.

4.2 Distinguish target families

Possible target families include:
A. Directly measured physical quantity, e.g. calibrated displacement, tilt, pore-water pressure, or soil moisture.
B. A future measured change over a defined horizon, e.g. displacement over the next H minutes.
C. A human- or expert-assigned ordinal condition score, provided the scale, evidence, inter-rater agreement, and limits are specified.
D. A derived engineering index with a documented formula and validated reference inputs.
E. A binary event outcome encoded numerically. This is usually a classification problem; using regression is allowed only with an explicit rationale and must not be described as probability by default.

These are alternatives, not simultaneous targets. The project owner and ML/system reviewer MUST select one target family and approve the evidence supporting it.

4.3 Target independence

The target MUST NOT be a deterministic restatement of the same input feature vector unless the intended task is explicitly feature reconstruction. For predictive claims, the target should be measured independently or at a future time, and the temporal protocol must prevent information leakage.

4.4 No unsupported risk claims

A model trained on synthetic labels, heuristic scores, or unverified sensor proxies may only claim to estimate that synthetic score/proxy. It MUST NOT claim to predict real landslides or estimate landslide probability without suitable independent ground truth and validation.

======================================================================
6. TARGET OPTIONS AND DECISION GATE
======================================================================

The following options are candidate directions only. This section does not select one.

Option A — Calibrated physical quantity
Example: estimate calibrated tilt angle, soil moisture, or displacement.
Advantages: clear units and measurable reference.
Risks: sensor-specific calibration, limited relationship to actual slope failure, and possible target/input circularity if the same sensor supplies both target and features.

Option B — Future change over a defined horizon
Example: predict change in calibrated tilt or displacement over a fixed future horizon H.
Advantages: defines a predictive task with a temporal target.
Risks: requires reliable timestamps, horizon definition, adequate independent episodes, and leakage-safe window construction.

Option C — Expert-assigned condition/instability index
Advantages: may combine several observations.
Risks: subjective scale, labeler disagreement, possible circularity, and no automatic interpretation as probability. Requires a written rubric, independent reviewers, and agreement analysis.

Option D — Engineering index from a validated physical model
Advantages: reproducible formula if inputs and assumptions are valid.
Risks: outputs inherit model assumptions and must not be called ground truth for real-world landslide outcomes without validation.

Option E — Event outcome
Example: whether a defined event occurred within horizon H.
This is naturally a classification target in many cases. If regression is retained, the project MUST document why, define numeric encoding, evaluate appropriately, and explicitly prohibit interpreting the raw regression output as calibrated probability.

Decision record MUST contain:
- selected option and rationale;
- rejected alternatives and reasons;
- intended user/action and non-use;
- supporting studies, measurements, or field evidence;
- ground-truth feasibility and risk;
- reviewer approval.

Until this decision is approved, model training may be exploratory only and any resulting model MUST be marked NOT FOR OPERATIONAL USE.

======================================================================
7. GROUND-TRUTH EVIDENCE REQUIREMENTS
======================================================================

7.1 Evidence hierarchy

For each label, record which evidence class applies:
- G1: traceable instrument/reference measurement with documented calibration and timestamps.
- G2: independently verified field observation with evidence, method, and reviewer.
- G3: expert annotation under an approved rubric with reviewer and disagreement handling.
- G4: derived value from a documented formula and approved source measurements.
- G5: synthetic, heuristic, or proxy label.

The hierarchy is descriptive, not a guarantee of quality. G5 labels MUST NOT be presented as observed real-world outcomes. The approved target contract MUST state which evidence classes are allowed for training and evaluation. The final test set SHOULD use the strongest feasible independent evidence for the target.

7.2 Minimum evidence record

Every labeled record/window MUST reference:
- label_id and target_contract_version;
- source session and raw data identifiers;
- target value and unit;
- event/measurement timestamp or interval;
- evidence class;
- reference instrument or observation method;
- calibration identifier where relevant;
- annotator/reviewer identifiers or controlled pseudonymous IDs;
- annotation timestamp;
- quality state and uncertainty;
- evidence file/reference and checksum where applicable;
- rationale for exclusions or adjudication.

7.3 Independent evidence

Ground truth MUST NOT be generated from the model output being evaluated. If a proxy derived from an input sensor is used as the target, the dataset documentation MUST state that limitation, and claims MUST be limited to estimating the proxy.

7.4 Uncertainty and disagreements

If a reference measurement has uncertainty, record it or reference the uncertainty specification. If annotators disagree beyond the approved tolerance, mark the label DISPUTED and route it to adjudication. Do not silently average categorical judgments or replace disagreement with a guessed numeric value.

======================================================================
8. TEMPORAL ALIGNMENT CONTRACT
======================================================================

8.1 Required timestamps

Use a documented time base. Store monotonic device time for ordering and elapsed durations; store wall-clock/UTC time only when a trustworthy clock is available. Record synchronization quality. Do not treat an unset or unsynchronized wall clock as accurate.

Each input window MUST identify:
- session_id;
- window_id;
- start timestamp;
- end timestamp;
- sampling/window configuration version;
- gap/dropout status;
- feature generation version.

Each target MUST identify:
- target measurement time or interval;
- whether it is contemporaneous, retrospective, or future;
- prediction horizon, if any;
- alignment rule version.

8.2 Contemporaneous estimation

For a target measured over interval [t0, t1], the contract MUST define whether the input window ends at t1, precedes t0 by a gap, or uses another justified relationship. The window MUST NOT contain measurements collected after the target time if the task is intended to estimate the target before it was known.

8.3 Forecasting

For a future target, define:
- prediction origin t;
- horizon H;
- target interval [t+H_start, t+H_end] or exact target time;
- any embargo/gap between input window and target interval;
- rule for overlapping horizons.

The exact horizon and embargo are TBD until approved. They MUST NOT be inferred from convenience or chosen after examining test performance.

8.4 Missing or irregular samples

Windows with gaps, stale channels, out-of-order timestamps, invalid calibration, or excessive missingness MUST be handled according to the approved data-quality policy. Missing target values MUST NOT be filled with zero. Interpolation is permitted only if scientifically justified, versioned, and approved for the target; the original missingness and imputation mask must be retained.

8.5 Window overlap and leakage

Overlapping windows from one event/session/site MUST remain in the same data split unless a documented group-aware design proves independence. Adjacent windows MUST NOT be randomly scattered across train, validation, and test. Apply any embargo required by the target horizon and temporal correlation.

======================================================================
9. LABEL STATES AND ELIGIBILITY
======================================================================

Recommended canonical target-label states:
- VALID: evidence satisfies contract and target is within the approved domain.
- MISSING: no target evidence available.
- INVALID_FORMAT: target cannot be parsed in the declared type.
- NON_FINITE: NaN or infinity.
- INVALID_RANGE: value outside approved range and not accepted by a documented exception.
- CALIBRATION_INVALID: required calibration absent, expired, or failed.
- STALE: target evidence is older than allowed for the defined alignment.
- DISPUTED: unresolved annotator/reference disagreement.
- LOW_CONFIDENCE: evidence exists but does not meet the primary training/evaluation threshold.
- SYNTHETIC: generated by simulation, heuristic, or proxy method.
- EXCLUDED: deliberately excluded with a reason.
- NOT_APPLICABLE: target is not defined for this sample under the contract.

Only VALID labels are eligible for the primary supervised training/evaluation set unless the approved contract explicitly defines additional states and their treatment. SYNTHETIC or LOW_CONFIDENCE labels MUST be separated or explicitly tagged and analyzed; they MUST NOT silently mix with high-quality ground truth. Invalid labels MUST NOT be converted to a numeric default.

Each exclusion MUST have a reason code and be counted in quality reports.

======================================================================
10. NUMERIC AND ENCODING RULES
======================================================================

- The stored label type MUST match the machine-readable target contract.
- Unit conversion MUST be explicit and versioned; values with different units MUST NOT be mixed.
- Float serialization MUST use a documented locale-independent representation.
- NaN and infinity MUST be rejected from the canonical training target.
- Clipping out-of-range labels is prohibited unless the contract defines it, provides rationale, and preserves the pre-clipped value and flag.
- Normalization/scaling parameters MUST be fitted on the training split only, then frozen and applied unchanged to validation/test/runtime.
- If the target is transformed for training, the transformation formula, parameters, version, and inverse transform MUST be stored.
- Evaluation metrics MUST be reported in the original target unit as well as transformed space when relevant.
- Numeric rounding MUST NOT erase meaningful changes; precision requirements are TBD per target.
- Categorical encodings MUST not be used as ordinal numeric values unless their order and distances are explicitly meaningful and approved.

======================================================================
12. TRAINING AND EVALUATION RULES
======================================================================

12.1 Training eligibility

Training pipeline MUST validate the target contract and dataset manifest before accepting data. It MUST fail closed if required versions, units, target values, or hashes are missing/mismatched.

12.2 Baselines

Report at least a simple baseline appropriate to the target, such as training-set median/mean for a continuous target or a justified persistence baseline for time-series prediction. Baseline selection must not leak validation/test information.

12.3 Metrics

Metric choice depends on the approved target:
- Continuous target candidates: MAE, RMSE, bias/mean error, and residual analysis.
- Ordinal score: ordinal-aware metrics and per-level error analysis may be required.
- Event-coded target: compare regression against a classification baseline; do not use regression merely to obtain a continuous-looking score.
- Physical forecast: report error versus horizon, operating conditions, and independent site/event groups.

These are candidates, not pre-approved metrics. The approved TCS and experiment plan MUST name primary/secondary metrics and thresholds. Thresholds MUST be selected before final test evaluation, not tuned to make a test result pass.

12.4 Evaluation splits

Use group-aware splits by site, event, deployment episode, or another independence unit appropriate to the data-generating process. Split policy MUST be documented before model selection. If data is too limited for an independent test, report that limitation and do not imply generalization.

12.5 Test-set integrity

The final test set MUST be frozen and used only for final evaluation, except for a documented test protocol revision. Repeatedly tuning model/hyperparameters against test results invalidates the test as an unbiased final estimate. Any re-use must be logged.

12.6 Reporting

Reports MUST include:
- target contract version and interpretation;
- data split IDs and hashes;
- counts by label state and evidence class;
- missing/excluded/disputed-label rates;
- performance overall and by site/event/condition where sample size allows;
- baseline results;
- uncertainty and known limitations;
- model artifact hash and inference metadata;
- explicit statement of what the model does and does not establish.

13. RUNTIME INFERENCE CONTRACT
======================================================================

Runtime firmware MUST treat the regression output as model_value/model_score until the approved target contract gives it a specific physical meaning and unit.

Runtime output record SHOULD include:
- model_value;
- target_contract_version;
- model_id/model_version;
- feature_schema_version/hash;
- inference timestamp;
- input window start/end;
- input quality status;
- model execution status;
- output validity status;
- calibration/configuration identifiers where applicable.

The firmware MUST NOT:
- label raw regression output as “probability of landslide” by default;
- convert model_value to alarm levels using undocumented thresholds;
- treat missing/stale/invalid sensor data as zero or “safe”;
- issue a valid target estimate when the input window violates required quality gates;
- silently use a model with mismatched target or feature schema.

If the target contract defines thresholds, their units, boundaries, inclusivity, hysteresis, debounce, reset behavior, and fault precedence MUST be defined in the appropriate alarm/interface contract. A threshold is not approved merely because it produces plausible demonstration behavior.

Invalid inference should produce a documented invalid/fault status, not a fabricated target value. Alarm/fault semantics remain governed by ICD and the approved alarm contract.

======================================================================
14. SAFETY, BIAS, AND CLAIMS CONTROL
======================================================================

Risks to assess:
- proxy labels incorrectly presented as ground truth;
- target leakage from input features or future samples;
- labeler inconsistency;
- reference instrument calibration error;
- missing severe-event examples;
- class/condition imbalance;
- site, geology, weather, mounting, or sensor-specific bias;
- synthetic labels dominating the dataset;
- model extrapolation beyond observed conditions;
- distribution shift after installation;
- alarm thresholds chosen from test data;
- confusing a condition score with probability or causal prediction.

Required controls:
- maintain an explicit target risk register;
- record evidence class and provenance for each label;
- keep test data independent by site/event/session as feasible;
- analyze performance by conditions and groups;
- report limitations and out-of-domain behavior;
- establish a monitoring/revalidation plan for any field trial;
- do not deploy as the sole safety control.

No claim of actual landslide prediction, calibrated risk probability, or safety certification is permitted solely on the basis of low regression error against a proxy score.

======================================================================
15. VERSIONING AND CHANGE CONTROL
======================================================================

Increment the target contract version whenever a change affects:
- target meaning or intended use;
- target family, unit, range, direction, or numeric encoding;
- reference method or evidence classes;
- labeling rubric or adjudication policy;
- time alignment, prediction horizon, aggregation, or embargo;
- label validity/exclusion policy;
- transformation or inverse transform;
- primary metric or acceptance threshold;
- runtime interpretation or threshold mapping.

A change to target meaning requires a new target contract version and normally a new dataset/model release lineage. Do not edit frozen labels or experiment records in place. Create a new version, preserve the old artifacts, and document migration/relabeling rules.

Each released contract MUST have:
- immutable version identifier;
- SHA-256 hash;
- change log;
- owner and reviewer;
- approval date;
- linked DSD/DOP/FSS/ICD/model versions;
- explicit compatibility statement.
